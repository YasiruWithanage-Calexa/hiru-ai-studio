# AI architecture: one package, built from parts

The design of [plan/2026-11-03/PLAN.md](../plan/2026-11-03/PLAN.md), in short. **Status: Phases 0 to 7 done; Phase 8
partly.** The core, the adapters, the steps, tools, knowledge bases and retrieval, the agents, the pattern library, 4 panels
and **all eight systems** exist (`echo`, `doc_ingest`, `canon_extract`, `structure_build`, `frame_render`, `script_split`,
`shot_producer`, `director_chat`). Each function runs the new engine when `AI_ENGINE=graph` (default `legacy`) and every
system is held to the old engine by the parity fixtures. **The legacy engines are still in place, on purpose**: nothing has
yet run against the hosted database or a live OpenAI key, so the switch back stays until a person has made that run
(see "Phase 8" in [IMPLEMENTED.md](../plan/2026-11-03/IMPLEMENTED.md)). The API's own model calls are not moved (it carries
no LangChain; that is a decision for you). Browse every part in [AI_CATALOG.md](AI_CATALOG.md) (generated by `hiru-ai catalog`).

## The idea

Agents, tools, knowledge bases, panels and whole systems are **independent parts**. Each is a folder with a
`component.yaml` manifest. A part is added, removed, switched off or rewired by editing its folder and, at most,
one line in a parent manifest. Nothing imports a sibling; everything is found by id through a registry.

## The stack

| Piece | Used for |
|---|---|
| LangChain 1.x | models, prompts, tools, `create_agent`, middleware |
| LangGraph 1.x | graphs, subgraphs, checkpoints, `interrupt()`, streaming |
| `langchain-openai` behind `get_llm` ([ADR 0003](adr/0003-litellm-in-process.md); LiteLLM is the later swap) | model tiers, retries, fallbacks, usage |
| `import-linter` | the layer and independence rules, checked in CI |

## Layers

Each layer may import only layers below it, and `contracts`.

```
core → rag → knowledge_bases → tools, steps → agents → panels → systems
```

| Layer | Holds |
|---|---|
| `core` | settings, `models.yaml` (tiers), `get_llm`, usage, `RunContext`, ports, registry, manifests, middleware, patterns |
| `rag` | embeddings, retrievers (pgvector, keyword, hybrid), rerankers |
| `knowledge_bases` | one folder per corpus: sources, ingest, manifest |
| `tools` | atomic actions a model may call |
| `steps` | deterministic graph nodes, no model (kernel score, settle, ripple, timing fit…) |
| `agents` | one focused agent per folder: prompts, schema, manifest, evals, tests |
| `panels` | groups of agents as subgraphs (`board`, `critics_judge`, `generate_critique`…) |
| `systems` | full flows, one per product job; a Cloud Run handler is ~20 lines around one |

`adapters/` (Supabase REST, storage, the image API) sit behind `core/ports.py` and are imported only by the
composition roots: `src/services/*/app`, `src/api`, the CLI. Tests and `hiru-ai run` use the in-memory fakes in
`core/fakes.py`.

Phase 2 parts: 13 steps (`scene_kernel`, `kernel_score`, `board_settle`, `ripple`, `refusal_screen`, `verbatim_check`,
`feeling`, `serialize`, `chunk`, `extract_text`, `canon_rules`, `bridges`, `stage_check`) and 11 tools (`scene_read`,
`dialogue_read`, `scene_write`, `shot_write`, `canon_write`, `structure_write`, `timing_check`, `veo_fit`,
`technique_lookup`, `image_generate`, `search_kb`). A step is `run(json) -> json`; a tool is `run(args, ctx) -> Result`
plus `as_tool()` for an agent's tool loop. Both carry `examples/basic.json`, which `hiru-ai run` runs.

Phase 2 added one more step later (`scene_listing`, Phase 4), so there are 14 steps.

Phase 3 parts: `rag/` (the pure `ranking`, `scope`, `hits` the API also uses; `embeddings`; `retrievers/` match_chunks,
keyword, hybrid, techniques; `rerankers`; the `KnowledgeBase` base) and six knowledge bases: `craft`, `guides`, `rules`
(prose, one `craft` corpus, rows replaced by source prefix), `cinematography` (the technique table), `techniques` (how agents
search it) and `production_docs` (filled by the doc_ingest job). `hiru-ai ingest <kb>|--all` indexes them.
An agent's `knowledge:` ids become the corpora `search_kb` may read (`core.scope`).

Phase 4 parts: 27 agents and two builders in `core/agents.py`. `structured` is one typed call (strict JSON schema, a usage
row, the fallback when the model is unavailable); `react` is a `create_agent` tool loop with the run's `RunContext`, and
`hitl` / `retry` / `fallback` middleware. An agent folder holds `schema.py` (Input, Output), `agent.py` (hooks:
`user_message`, optional `fallback`, `finish`, `images`, `output_schema`), `prompts/system.md` (static), `evals/cases.yaml`
(input, scripted reply, expected output) and `tests/`. `hiru-ai run agent <id> --input case.json` runs one alone.

Tools (plan/2026-11-04, Phases 0 and 1): 28 tools, 17 of them new. Every tool follows one contract, checked by `hiru-ai
validate` and the generated tests:

- `effect: read | stage | write` in the manifest. `read` changes nothing; `stage` leaves a card in the `staging` port that a
  person accepts (`change_propose`, `memory_propose`); `write` changes stored data and is called by a system in code, never
  listed on an agent (`validate` refuses it). An agent sees at most 8 tools, sorted by id, built once, so the tool block is part
  of the cached prompt prefix (`static_first` checks it).
- The description a model reads is `summary` + `guide`; the guide says what it returns, when to use it, and when NOT to (with
  the tool to use instead). Arguments hold only what a model may choose: production, scene in scope (`RunContext.scene_id`)
  and the person's own words (`RunContext.said`) come from the run.
- Results are small: `response_format` concise by default, paging (`page`, `page_size`, `next_page`, `total`), codes and
  numbers (`C02`, `S03`, `E1S2`) instead of ids, and a cut at the manifest's `max_result_tokens` that says which argument
  narrows it. A refused call answers `{"error", "how_to_fix", "example"}`; a failed port answers a clear error, never a crash.
- `core/tooling.py` is the runtime (and `core/views.py`, `core/trial.py` hold what several tools share); one telemetry event
  per call lands in `RunContext.tool_events`. `core/middleware/react.py` adds `limits`, `clear_old_results` and `tool_retry` to
  the loop. `token_usage` gains `component`, `component_version`, `prompt_hash`, `tool_calls`, `tool_result_tokens` (schema v10,
  written only with `USAGE_DETAIL=true`). `hiru-ai eval` reports tokens, model calls, tool calls and tool errors per agent,
  scripts a case's `tool_calls:`, and compares two manifests with `--ab old.yaml,current`.
- `hiru-ai new tool <id> --effect read --wraps <step>` scaffolds a tool with the contract filled in; `hiru-ai run tool <id>
  --input case.json --format concise|detailed` runs one and prints how many tokens a model would read.

Tools in use (plan/2026-11-04, Phases 2 and 3):

- **The tools form.** `chat_answerer`, `options_writer`, `translator` and `shot_critic` each have a `with_tools:` block in
  their manifest: the same agent as a `react` loop with its own tools (at most 8, none that writes), its own prompt and its
  own loop caps. `Agent(registry, id)` runs it only when `AGENT_TOOLS` (a setting, empty by default) names the agent;
  `hiru-ai eval <agent> --tools` runs its scripted cases and `--ab base,tools [--live]` compares it with the single call.
  The callers pick the lighter message when `agent.uses_tools`: the chat answerer gets a one-line summary of the scene in
  place of the shot list, and the options writer no memory list (it reads it with `memory_search`).
- **Scope.** `director_chat` puts the scene in scope (`RunContext.scene_id`) and the person's own words (`said`) in the
  context it hands every model of the turn; the search tools' passages are cited like the director's own search was.
- **Staged cards.** After the reply the turn reads `staging.staged()` back and shows each card as an option of the options
  card (`systems/director_chat/staged.py`): a `change` card applies its operations, pinned to the shots, through the same
  code as a button press; a `memory` card is a message to the board ("Remember from now on: ...").
- **The critic reads the drafts.** `shot_producer` reviews a scene's designs before they are saved, so the critic's tools
  read the drafts through an overlay of the scenes port (`systems/shot_producer/drafts.py`), not last time's design.
- **Outside the agents.** `hiru-ai mcp` serves every active `read` and `stage` tool over MCP on stdio (scope from the
  command line, `readOnlyHint` from `effect`, never a `write` tool); each tool call is an OpenTelemetry span (id, version,
  effect, tokens, error; no arguments) that exports nothing until a person installs an exporter (ADR 0008); `hiru-ai review
  <log>` reports per-tool calls, errors and cut answers from the log.

## Rules that make the parts independent

1. **Registry, never a sibling import.** Code asks for `registry.agent("translator")`. A step or tool that builds on
   another step names it in `uses:` and gets it from `core.parts` ([ADR 0009](adr/0009-parts-reach-siblings-by-id.md)).
2. **Typed seams.** Agents declare `Input`/`Output`; the panel maps state in and out. No free-text hand-offs.
3. **Injected dependencies.** `RunContext` carries scope, actor, job id and the ports; there are no globals. A tool's
   arguments hold only what a model may choose: never the production, the actor, the corpora or a port.
4. **Deterministic rules are parts too.** Critics (agents) write notes; the judge (a step) is code and picks.
5. **Cross-cutting rules are middleware**, attached by name in the manifest: usage row per call, uploaded text
   is data, absent-safe, language guard (only `writes_dialogue: true` parts may change a line), static-first prompts.
6. **Models through one door.** Everything calls `get_llm(tier)`; tiers live in `models.yaml`.
7. **Tests live in the part's folder.** Deleting a part deletes its tests.

## How it is kept honest

- `python scripts/lint_imports.py`: the service boundaries, the `hiru_ai` layers, sibling independence and
  "only `core.llm` imports OpenAI" (17 contracts in `pyproject.toml`, among them "adapters import only core", "only a composition root imports an
  adapter" and "parts reach the database only through ports"). Runs in CI next to `mypy`.
- `hiru-ai validate` (built): ids resolve (`uses` too), schemas line up, a tool names only real run ports, every agent
  has a prompt and an eval case.
- `hiru-ai catalog --check` in CI: [AI_CATALOG.md](AI_CATALOG.md) is generated from the manifests and must be current.
- `hiru-ai eval`: every agent's eval cases, scripted (CI) or live and A/B (a person).
- Generated contract tests over the registry (`tests/hiru_ai/test_contract.py`): every step and tool has an example
  that runs from the command line, a tool uses only the ports it declares and its `effect` says what it may change; Mermaid snapshots of every graph (Phase 5).
- **Step parity** (`tests/hiru_ai/test_steps_parity.py`): each step against the legacy engine function it was ported from.
- **Parity fixtures** (`tests/parity/`, Phase 0): the whole outcome of every service on scripted inputs, recorded
  from today's code. The new graphs must reproduce them before a function switches over.
