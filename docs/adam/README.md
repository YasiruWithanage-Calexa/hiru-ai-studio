# Shot Planner Adam: architecture

Adam is a second, separate shot planner (plan: [plan/2026-11-04b](../../plan/2026-11-04b/PLAN.md)). `script_split` is not
changed. A production or a scene chooses which one plans its shots, and both write the same `shots` rows.

**Imagine first, then cut.** Analyse the scene, conceive three treatments, imagine the viewer's experience as ordered
moments, stage it, design the cards and the sound, screen with four critics and keep the better version by a score in
code, then write the rows. The rule changes from "never invent" to **never invent story; always elaborate the picture**:
a moment is SCRIPT, IMPLIED or ELABORATION (a closed list of 13 kinds), and INVENTION is refused in code.

## Where it lives

```
src/libs/hiru_ai/<layer>/adam/       one `adam` folder in each of the six layers (group.yaml marks it)
src/libs/contracts/adam/             the plan as typed data (plan.py, tiers.py, mapping.py) and what a model writes (wire.py)
src/services/shot_planner_adam/      (Phase 6) the Cloud Run function
tests/adam/   tests/eval/adam/       tests; the gold set (scenes, masters, baselines, rubric, probes)
docs/adam/                           this folder
```

Deleting those folders removes Adam; `hiru-ai remove --group adam` lists them and everything outside that still names it.

## The parts built so far

| Part | Kind | What it does |
|---|---|---|
| `adam_fidelity` | step | Every script block and line once, in order; added moments only from the allowed kinds, with people present and objects that fit the place. A break is dropped (an added moment) or sent back (the script). |
| `adam_fit` | step | Moments and cards on the Veo clock (4/6/8 s, 2.2 words/s). Reports overruns, the runtime against the envelope. Never trims a line. |
| `adam_continuity` | step | The 180° line, eyelines and screen direction, a person in two places without a move, props that change hands unseen. |
| `adam_feasibility` | step | What Veo renders badly (readable text, mirrors, fast hands, touching, crowds, a line across two takes) and the known fix. |
| `adam_score` | step | The craft score: fourteen signals, each naming the card it is about (plan 2026-11-04c added `coverage`, weight 3, and `one_job_per_card`). A fidelity break, an overrun or a required face lost to the other plan loses first. The percent is the craft share times the coverage share. Picks the better of two plans. |
| `adam_coverage` | step | The coverage grid (beats by people) and the faces the analysis says must be seen: the turn, the other person at it, the irony, each subtext, each person's stake. Holes are named. The designer is told them before it designs. |
| `adam_split` | step | Repairs a crowded card in code: a longer take, or a split at a moment boundary; never a deletion, never a trimmed line. |
| `adam_ledger` | step | Every moment the writer made ends as kept, dropped by fidelity, removed by a person or removed by an operation for a note; one that left with no record fails the scene. |
| `adam_distinct` | step | The three treatments of a scene differ on purpose: every pair differs on at least two of size arc, point of view and sound concept, and in name and stance. |
| `adam_film_grammar` | knowledge base | 16 principles, 40 devices, the house drama notes (draft) and the Veo notes. |
| `adam_dramaturg` | agent, high | ① What the scene is about: the value that turns, beats, wants (verbs), whose scene it is, what the audience knows, baseline, break, key moment. |
| `adam_director` | agent, high | ② Three treatments (restrained, intimate, heightened) that differ on purpose: concept, size arc, POV, sound concept, plant and payoff, the one rhythm break, entry, exit, ending image. |
| `adam_moment_writer` | agent, high | ③ The viewer's experience as ordered moments (script, implied, elaboration), and the ids of the plant, the break, the ending and the POV handover. |
| `adam_blocker` | agent, medium | ④ Who is where in each moment, and why they move (power, avoidance, approach). Copied from the stager (see its `ORIGIN.md`). |
| `adam_shot_designer` | agent, high | ⑤ Moments grouped into 4/6/8 s takes and designed as shot cards; a line is named by id, never written. |
| `adam_sound_designer` | agent, medium | ⑤ The scene's sound map and each card's sound. |

Every agent has a **wire shape** (`contracts/adam/wire.py`): what the model is held to in strict JSON-schema mode (no
default, no free-form mapping), with a method that turns it into the plan's shape. None has a fallback: with no model
the job fails clearly (plan §5.5). They read the film-grammar passages and the device library as INPUT, passed in by the
system (an agent here is one call and cannot search). Each prompt carries one worked example drawn from the gold set
(`refuses_money`), generated by `tests/adam/stages.py`; that scene has no eval case.

The agents run in order, each fed what the one before returned (see `tests/adam/test_stages.py`, which runs all six with
scripted answers and then the five code steps over the result):

```
dramaturg → director ×3 → adam_distinct → [choose] → moment writer → adam_fidelity (+ bind ids)
          → blocker → shot designer → adam_fidelity (cards), adam_fit, adam_continuity, adam_feasibility
          → sound designer → adam_score
```

## Phases 5 to 10 (built, none run on a real model)

| Part | What it does |
|---|---|
| `adam_critic_audience`, `_editor`, `_opportunity`, `_fidelity` (agents, medium) | Four lenses, each at most four notes and a 1 to 5 score. The fidelity critic alone reads the code's report. |
| `adam_reviser` (agent, high) | One revision as OPERATIONS (replace, insert, remove a card; add, remove a moment), never a fresh plan. |
| `adam_screening` (panel) | The four critics in parallel, `adam_notes` merges, the reviser revises once, `adam_fidelity` drops an added moment that invents story, `adam_score` keeps the better version. The critics' scores are stored for a person; they decide nothing. |
| `adam_notes`, `adam_passages`, `adam_write`, `adam_trim` (steps) | Merge the notes and write the code report; pick the film-grammar and device passages from the base's own files; write the rows (shot + card + intent, the lines bound, the fit report in the classic shape, the stored plan); propose where an editor would cut a take. |
| `adam_distinct.choose` | The quick score on the three treatments alone, for when no person picks. |
| `adam_shot_planner` (system) | The whole pipeline for each scene (`scene.py`), waves of four scenes, a time budget, a send-back-once on a script fault or an overrun, no rules fallback: with no model the job fails and names the classic planner. Edits: `{"remove_moment"}` (no model) and `{"treatment"}` (plans the cards again from the stored analysis). |
| `services/shot_planner_adam` | The Cloud Run function (job kind `plan_scene_adam`, port 8209). |
| Storage | `shots.card`, `shots.planner`, `scenes.adam` (one migration, `Database/schema_v11.sql`); the production's choice is `settings.shot_planner`. |
| After the plan | A shot with a card stores an intent `by = "adam"`, so the intent agent is skipped; the DoP is told the card's camera as fixed; performance, sound and silence reach the Veo prompt; `prompt_lint` checks them. |
| Editorial | `contracts/adam/editorial.py` plans cuts; `infra/assemble` `/cut` trims takes and lays sound across cuts (pre-lap, carry). Off unless `settings.final_cut_trim`. |
| Phase 10 tools | `scripts/adam_live.py` (live runs; refuses without `--yes`), `scripts/adam_ab.py` (counts the blind A/B against the targets; suggests weights). |

The interface side is `hiru-ai-studio-interface/src/features/adam/`.

## Plan 2026-11-04c: the system defends the scene

[plan/2026-11-04c](../../plan/2026-11-04c/PLAN.md) (status: [IMPLEMENTED.md](../../plan/2026-11-04c/IMPLEMENTED.md)) came from
three live runs that passed every check and got worse. The yardstick could not see the other person's side, so it now
can (`adam_coverage`) and is tested by mutation (`tests/adam/test_score_mutations.py`); a revision cannot win by deleting
(`adam_split`, the rank counts the required faces it loses); nothing leaves the plan without a record (`adam_ledger`,
`report.history`); the reviser answers every note (`dispositions`); the designer is told the faces it must give a card;
the script's open questions go to a person (`questions`). The stored report gains `coverage`, `history`, `ledger`,
`questions` and `density`.

## Plan 2026-11-05b: every scene at once

[plan/2026-11-05b](../../plan/2026-11-05b/PLAN.md) changes **when** scenes are planned, not how. A delivery plans up to
`ADAM_WORKERS` scenes at once (default 10; lower it if the OpenAI account's gpt-5 limits are low) in a rolling pool: each
scene is written as it finishes, and no new scene starts after `TIME_BUDGET_S` (900 s) of the 1800 s function deadline,
so the rest go to a fresh delivery. A continued delivery now keeps the request's `mode`, `replan` and `screening`. The
function timeout (`deploy-functions.yml`) and `FunctionSpec.deadline_s` (`task_manager.py`) must both say 1800.

## Plan 2026-11-05: the scene in one take

[plan/2026-11-05](../../plan/2026-11-05/PLAN.md) (status: [IMPLEMENTED.md](../../plan/2026-11-05/IMPLEMENTED.md)) came from the
cost of a build ($5.16 for 9 scenes, 93 % of it gpt-5 reasoning). `ADAM_MODE=take` plans a scene with **one gpt-5 call** and a
**ladder of small fixes**; `staged` (the default) is everything above, untouched.

```
adam_take (high, 600 s) → adam_write → fidelity → rung-0 mend → fit/split → adam_sound_designer → trim
   → checks and score → adam_critic (one call, four lenses) → adam_problems → the ladder → finish
```

| Part | Kind | What it does |
|---|---|---|
| `adam_take` | agent, high | The analysis, the chosen treatment and two pitches, the moments, the staging and the cards (no sound) in one answer (`TakeWire`), given the facts code knows (each line's words and the shortest take that holds it). |
| `adam_critic` | agent, medium | The four lenses in one call: notes tagged by lens, one score per lens. |
| `adam_problems` | step | Rung 0 (a script line goes to the card that shows its moment) and the sort of what is left into problems: mechanical, local, creative. |
| `adam_fixer` | agent, medium | ONE problem in, the reviser's operations out. The tier is chosen per call. |
| `fixer.yaml`, `ladder.py` | system | Which tier each rung of each kind of problem runs on (`small` → `medium`, `big` → `fixer`, gpt-5 at low effort), and the loop: after every fix code checks the whole plan; a refused fix goes up a rung; what no rung fixes is reported. |

A plan keeps `input_hash`; a rebuild whose input is unchanged keeps the plan ("Plan with Adam" always plans). The cost helper and
the spike: `scripts/adam_cost.py`, `scripts/adam_live.py --mode take`, `scripts/adam_take_spike.py`.

## The rules that keep it apart

1. Ids in an `adam/` folder start with `adam_`; an `adam_` id outside one is refused.
2. A part of the group names only parts of the group; nothing outside names one inside.
3. Adam's modules import only their own `adam` folder, a lower layer's, `hiru_ai.core`, `hiru_ai.rag` and `contracts`
   (import-linter plus `tests/adam/test_isolation.py`); nothing outside imports them.
4. `contracts.adam` imports only `contracts.timing` from the rest of `contracts`.
5. Reuse is by copy with an `ORIGIN.md`, not by import.
